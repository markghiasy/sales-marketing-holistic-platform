# 先找全证据，再升级关系网络检索

**现在的 demo 用规则匹配、有限邻域扩展和两次 LLM 调用检索图与 context，没有 BM25、向量召回或语义重排。** 它已有时间过滤与来源校验，但候选主要按沟通活跃度截取，证据按 ID 截取，无法保证最相关材料进入答案。当前只有 24 位联系人，优先让全部合格候选参与相关性评估，并保证关系路径、时间和证据完整。再用受控实验决定是否增加混合检索。以下区分现有实现与工程提案；Graphiti、Hindsight 均是参考方案，未接入当前后端。

## 现在搜索的是标签和有限邻域，context 是结构化拼装

图扩展先过滤审核状态、获知时间及事实有效期，再按 source/target 双向扩展；结果相当于**无权、无向、限定跳数的可达搜索**，实现上逐轮扫描边池。它不是最短引荐路径算法。非 owner 焦点禁止通过 owner 中转；activity 衡量的是联系人与 owner 的沟通，不是焦点到候选的关系权重。（[projection.py](../../../adapters/network/projection.py)）

| 场景 | 当前算法与边界 | 优先优化（提案） |
|---|---|---|
| 图展开 | compact 一跳；expand 1–3 跳；上限分别为 8 节点/12 边、50/100 | typed adjacency＋frontier BFS；裁剪时保留桥梁和完整路径 |
| 快速找人 | regex 别名、姓名匹配；require 硬筛选，prefer 排序；无法解释的词触发澄清 | 保留精确筛选，增加类型化命中原因 |
| Agent 找人 | LLM 规划最多 4 个 lookup；姓名/有来源标签字面 OR；沿活跃度顺序取前 12 人 | 全候选相关性评分；搜索实际工作与原文证据 |
| 人物/组织/项目 context | 拼接直接事实、成员、共同背景、工作记录及 follow-ups | 分视图定义字段和允许边；显式传播 history 等查询参数 |
| 最终答案 | 第二次 LLM 合成；证据按 ID 取前 40 条 | 按需求覆盖、完整路径、去重与 token 预算选择 |

以上来自现有代码。`entity_context` 重建默认查询，只继承 focus/as_of；`compact_claim` 又省略时间字段，因此底层虽已过滤，模型却看不到完整时态。来源 ID 白名单与事实栏原文展示能约束引用，不能单独证明策略建议合理。（[search.py](../../../adapters/network/search.py)、[context.py](../../../adapters/network/context.py)、[agent.py](../../../adapters/network/agent.py)）

## 展示图与检索图需要不同预算和路径语义

**UI 展示 cap 不应决定问答能检索到什么。** 建议另设 RetrievalResult，返回命中原因、有序路径、每条边的时间/来源和截断原因。保留终点就保留必要桥梁；放不下完整路径时，应明确部分检索。现有活跃度门槛只适用于“最近联系的人”，不宜成为通用相关性硬筛选。

人物视图围绕个人事实、直接交往和工作；组织视图围绕成员任期、项目及有来源工作记录；项目视图围绕职责、交付、阻塞和待办。**A—组织—B 只能证明共同背景**；只有逐边支持的人际联系链才可建议“先询问 A 是否愿意引荐”，仍不能保证意愿。小图先做受约束路径枚举，无需先上复杂路径权重。这与 Microsoft local search 结合实体结构和原文的方向一致。（[Microsoft Local Search](https://microsoft.github.io/graphrag/query/local_search/)）

## Cybertest 应按目标检索，语义相似不等于专业能力

建议管线为：**目标分解 → 时间/状态硬过滤 → 全候选评分 → 相关实体有限扩展 → 覆盖驱动证据包 → 必要时补查一次 → 带未知项的回答**。需求显式区分 must/prefer/exclude，并标明需要一个人满足还是多人共同覆盖；**OR 召回只是候选池，不等于满足全部能力要求**。Cybertest 按用户给定的“面向 vibe coding 的授权 AI-agent 对抗测试”拆成评测方法、工程实现、安全专长、试点资源及潜在引荐。Engineering/Research 产生相邻候选，不能直接满足“已有对抗安全测试经验”。

24 人先建立附原文和 evidence ID 的精简人物卡，对全部候选评分；同时保留 evidence 级搜索。小语料直接重排全部段落是已有可行模式，不必先部署向量数据库。（[Sentence Transformers](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)）

证据包建议保留 `observed_at`、`valid_from/to`、需求 ID、原文短摘和来源绑定；正文只放一次。先保证关键需求、冲突/修正及每条路径的全部边证据，再填充其他材料。输出区分“支持、反证、未知”，未知再分未搜、预算截断、已搜未发现。短期记忆只保留已确认目标、已查范围与来源 ID，策略假设不能回写为人物事实。Hindsight 的多路检索与预算输出可借鉴，但其记忆 benchmark 不代表此处决策效果。（[Hindsight §3–4](https://arxiv.org/html/2512.12818v1)）

## 混合检索值得试，但应晚于证据选择修复

下一阶段对实体卡和证据分别做 **BM25＋多语言 dense → RRF → rerank**，再定向扩展图。BM25保留精确词，dense 补近义与跨语言召回；RRF 按排名融合，避免直接相加尺度不同的分数。（[RRF 官方说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)）Graphiti 已提供类似组合，部分 cross-encoder recipe 再加入 BFS；不是所有默认搜索都执行 BFS。（[官方 recipes](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/search/search_config_recipes.py)）

短证据可先加确定性前缀“人物—项目—时间—事实类型”，借鉴 contextual retrieval 恢复语境，不生成额外能力。Anthropic 的相关实验支持该方向，但不能将其文档检索收益外推本项目。（[Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)）中文问题对英文资料必须单独测试；现有 Claude key 也不等于 embedding 服务，需独立供应商或本地模型。（[Claude embeddings](https://platform.claude.com/docs/en/build-with-claude/embeddings)）**眼下不部署重型 GraphRAG/PPR 系统**；全库社区摘要和整体后端迁移留待明确的多跳/全局需求。

## 下一小版本用可归因的实验决定去留

**下一版范围**：先拆开展示与检索结果，保留时间、路径闭合和 coverage；再用全候选评分替换活动/ID 截断，加入去重与输入 token 预算；最后只对关键未知触发一次定向补查。保持现有身份、审核、时态和引用规则，补查无新增有效证据即停止。

建议固定快照建 32 题：Cybertest 策略、能力缺口、引荐路径、项目跟进各 8 题，分开发集和不参与调参的 held-out 集。纳入中文/英文改写、业务名替换、低频但合格联系人、同组织不认识、过期关系、晚获知修正、缺失来源和 ID 重命名。Anthropic 也建议从真实失败的小任务集起步，并用人工校准评分器。（[Agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）

消融依次比较当前版本、全候选评分、去重/预算打包、需求覆盖/完整路径、一次补查，最后比较 BM25、dense、hybrid 与 rerank；同模型、同问题、同预算，多次运行。测 evidence recall@预算、需求覆盖、完整路径率、未来证据泄漏、无依据能力/认识断言、建议可执行性及 P50/P95 延迟和 token。最近 Haiku 的 7,037 输入/1,015 输出 token 只是单次 smoke test，不能证明质量或成本改善。最终选型依据应是**在固定预算下更完整地支持决定，并准确解释未知**，而非答案更长或模型更新。
