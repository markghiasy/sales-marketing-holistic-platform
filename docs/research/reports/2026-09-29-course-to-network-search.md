# 从 INFS7410 Week 8–9 到战略网络检索：方法选择与实验路线

核对日期：2026-09-29。范围：阅读 Eva 的 Week8–9 教案及内容溯源记录，补看 Week5–7 的相关章节结构，对照当前 network demo 代码，并核实研究原文。本文是设计建议，不是算法上线或效果验证；没有修改教案、安装模型、调用付费 API 或改动运行中的 demo。

## 1. 教案与项目的直接联系

主要材料：[Week8–9 教案](<C:/Users/Eva Ng/Desktop/CPU 2026 2nd semester/INFS7410_2025/05_周课教案/INFS7410_Week8-9_教案.md>)。Week8 的 neural reranking、passage aggregation 和级联排序，Week9 的 query routing/rewriting、context selection 和 attribution，恰好分别对应我们的候选排序、多人多来源证据汇总、战略问题理解与回答核验。

现有代码 `adapters/network/retrieval.py`：`matches` 使用大小写归一化后的词集合包含关系；`people` 按命中检索词数量排序；搜索材料来自有来源的 claim/profile/strategy/work records。`pack` 已按未覆盖需求与字面相关性挑选完整证据包，并去重与限制字节预算。这不是 BM25、dense retrieval 或 neural reranking；原文没有绑定到可检索记录时，也不能假定它已被全量索引。中文连续文本的分词、跨语言和同义表达需要单独验证。

## 2. 最值得迁移的方法

### A. Week9：Query routing + Rewrite–Retrieve–Read

将商业目标拆成多个独立检索需求，同时保留用户原文、明确条件、否定条件与时间范围。每个改写记录 origin=user/inferred；推断出的理想条件不自动成为必须条件。针对各需求分别搜人、组织、项目、原始证据，保留各路候选再合并，避免一个占词量大的技术主题挤掉资金、渠道或试点需求。

例如“找能推动安全产品试点的人”可以分别搜索已有安全评测经验、组织试点需求、客户接触渠道、决策参与角色；但预算、采购权限和愿意介绍都必须另有证据。原始查询始终保留为一路，减少改写漂移。借用 Rewrite–Retrieve–Read 的模块分离，不意味着第一版复现其强化学习训练。[论文](https://aclanthology.org/2023.emnlp-main.322/)

### B. Week5/8：混合召回，再进行 query–evidence 联合重排

先建立可复现的 BM25 基线，再与多语言 dense retrieval 并行召回。用 RRF 融合各路排名，不直接相加 BM25 与余弦分数。RRF 窗口和候选数仍需实验，不因采用公式而消除调参需求，也不意味着必须部署 Elasticsearch。[RRF 官方说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

Week8 monoBERT 的联合 query/document 打分可以迁移为预训练 reranker 实验。重排单位优先是“需求 + 带主体/时间的原文片段”，不是整个人的所有聊天拼接。先高召回得到候选，再对有限候选重排，符合课程的多阶段排序。第一阶段没召回的证据，纯重排无法补回来。[Sentence Transformers 官方说明](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

[Qwen3-Reranker-0.6B 官方模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)对应教案 practical 中值得纳入对照的候选；是否适合本地部署，应测实际中英问题、否定句、归因、硬件、并发与延迟，不预先宣称它是最佳或直接替换 Claude。专用 reranker 负责相关性，Claude 继续负责目标规划与策略合成。

### C. Week8：Evidence aggregation，先证据后主体

课程的 passage-to-document 聚合可以启发 evidence-to-person/organization 聚合，但迁移规则是本项目设计，不是论文验证过的商业画像算法。

建议按“需求 × 实际主体”构建证据矩阵：每格先保留最强的直接相关原文，再附有限、去重且独立的佐证。不能直接 SumP 所有聊天分数，否则消息多、重复转发多的人可能占优；也不能仅用一个全局 MaxP，否则一条很相关的技术经历会遮住渠道或预算缺口。反证和未知保留为独立状态，不能被多个正相关文本抵消。

PARADE 的原文也显示，复杂表示聚合更适用于相关信息分散的长文档；当答案集中在一个段落时，较简单的方法可能更好。我们先做可解释的分需求聚合，再考虑训练复杂聚合模型。[PARADE](https://arxiv.org/abs/2008.09093)

### D. Week9：按需求组织 context，而非按分数堆文本

将每个需求的支持、限制/反证、未知项放在一起；保留实际主体、原文、日期、来源 ID 和完整关系路径。抽取式压缩与去重优先于改写原文；不能删掉 not、过去时、条件承诺或“代表某组织转述”的归因。预算内保留不同需求的证据，而非让同一类高分材料填满上下文。

Lost in the Middle 说明被研究的模型对证据位置敏感；不能把早期模型实验直接当作当前 Claude 的定律，应固定证据集做位置扰动实验。[论文](https://arxiv.org/abs/2307.03172)

### E. Week9：Attribution / RARR 启发的回答核验

现有来源 ID 白名单能检查引用存在，却不能证明引用支持结论。生产前应增加 claim–evidence 级检查：这条原文支持“此人有经验”，还是只支持“此人正在找有经验的人”？“组织有采购需求”不能变成“消息发送者掌握采购权”。

借鉴 RARR 的研究与修订思路，建议对生成的事实性陈述验证 support/contradiction/insufficient，并修订无支持的断言；模型核验结果仍不是事实证书。策略建议和已观察事实分开。补查受权限、时间和预算约束，不为既定答案无限寻找佐证。[RARR](https://aclanthology.org/2023.acl-long.910/)

### F. Week8：LLM listwise / setwise，作为小候选集实验

在少量候选上，可比较专用 reranker 与 Claude listwise/setwise。记录输入顺序敏感性、重复运行一致性、合法且唯一的 ID、额外调用数和超时回退。暂不把多轮 LLM 比较作为默认主路径。

Pairwise 的二次成本属于全配对实现；用排序算法减少比较次数是另一种实现选择。Setwise 的实验收益依赖模型与排序配置，不能把课堂中的百分比当作本系统 SLA。Pointwise 自报分数不等于经过校准的概率，更不是商业机会成功率。详见配套主来源核对笔记。

## 3. 暂不优先的选项

- CiC：在很小且固定、权限一致的证据集合上可作全量 context 基线；不默认把生产消息库全塞入 prompt。
- PARADE/duoBERT 自训练：先有足够任务标签和可重复收益证据再投入。
- 全配对 LLM 排序：候选多时调用数高，先与专用 reranker 比较。
- 截图/VLM 检索：等合同、演示文稿、复杂 PDF 附件成为核心数据时再开视觉检索分支；不能替代人物身份、归因和时间记录。
- DiffRetriever/生成式索引/更多复杂检索器：可以做研究对照，当前没有证据表明它们比清晰基线更值得优先投入。
- 主动加入随机噪声：Power of Noise 报告的是受控实验结果，合理启发是评估上下文组成，不能直接导出“生产里加无关材料更好”。[论文](https://arxiv.org/abs/2401.14887)

## 4. 建议实验流水线（未实施）

用户目标 → 需求分解/路由 → 授权与时态过滤 → 分需求 BM25 + multilingual dense → RRF → 有限候选 reranking → 证据归属/限制检查 → 人物与组织的需求覆盖 → 四范围内有来源的路径补充 → 有预算的证据包 → Claude 回答 → 陈述与证据核验。

显式指定人物/组织时，精确身份查找和确定性图遍历应并行提供候选，不必强迫一切都先经过向量检索。不得将共享公司等关系范围转换为统一亲密度。检索、路径与核验各阶段均需保留权限与时间约束；索引与缓存的隔离和更新不能靠生成阶段补救。

初始候选深度可比较每需求 20/50/100；这些是实验配置，不是性能承诺。规模看可索引证据数量与 token，而不仅是联系人数量。

## 5. 最小可归因评估

沿用先前建议的 32 题起始集，但纳入 Mark 的真实业务目标：试点/需求发现、合作或渠道、资源与能力、项目跟进各 8 题。分开发和 held-out；同一题的中英文改写与近重复必须在同一分组，避免泄漏。授权真实数据与合成边界用例分别报告，不能混作客户效果。

依次比较：现有 lexical 基线 → BM25 → BM25+dense+RRF → 加专用 reranker → 分需求聚合/打包 → 可选 LLM 重排与回答核验。固定 corpus snapshot、查询、模型与预算，生成步骤重复运行。

指标分层：证据 recall@k/预算、排序 nDCG@10、需求覆盖、人物/组织归因错误、否定/时态错误、完整路径率、权限与未来证据泄漏、回答证据支持率，以及 P50/P95 端到端延迟和实际成本。相关性与证据支持要分开标注；reranker 高分不能充当真实性判断。

主要收益假设：让低频但相关的人被召回，让噪声少占 context，让用户看到每个战略需求由谁、凭什么支持。没有在本项目运行上述模型实验，所以目前不报告提升比例或生产达标结论。

## 6. 从课堂概括到工程实现，需要保留的限定

- PARADE 并非“聚合越复杂一定越好”；原文报告不同信息需求下，简单聚合也可能更好。
- Pairwise 并非必然全配对；全配对、排序比较和有限 top-k 的调用复杂度不同。
- Setwise 不仅有读取 logits 的实现，也支持生成候选标识符的方式；API 接口条件要按所用模型检查。
- Qwen3-Reranker 是 decoder reranker，支持 CrossEncoder 接口不代表它变成了 BERT encoder。分数归一化也不证明事实正确或任务成功。
- Transformer 的标准稠密 attention 计算复杂度，不能直接等同于 API 账单或端到端延迟的平方增长。线上预算应测真实 token、缓存、并发和耗时。
- 课堂实验中“0.8%/62%”“噪声提升”等数字不能外推到 Mark 的任务。也不能把早期长上下文实验解释为所有现代模型的固定性能排序。

## 7. 生产容量与延迟要求（Eva 补充，2026-09-29）

Eva 明确提出：搜索慢同样是上线问题；老板的联系人网络预计比 Mark 更大。这是容量需求，不能继续按 24 个合成人物来决定生产方案。

### 已知基线与未知量

Mark 在此前提供的反馈中报告：Outlook、LinkedIn export、WhatsApp 三渠道，24,222 条消息，单个 PostgreSQL。该数字是客户当时报告的消息量，不是当前库的实测值，也不是联系人数量。老板的网络更大来自 Eva 的描述，具体数目尚未提供。上线前只读盘点：去重消息、联系人/组织、可索引证据段、事实边、正文 token、附件、每日新增/修改、活跃租户、并发查询和查询组合。

### 当前代码中可确认的延迟/容量风险

- 每次 answer 新建 NetworkRetrieval，扫描与构造记录及邻接结构；people 多次按词扫描并重复分词。未来不能让每次用户查询重建完整索引。
- planner 携带实体 catalog；该输入会随实体数量增长，不能简单把老板全部联系人交给模型先选。需要精确身份入口和索引检索缩小候选。
- 默认路径依次执行规划和合成两次模型调用，每次调用前另有远程 count_tokens；即通常存在四次顺序执行的 provider 请求。代码能确认调用结构，不能据此断言哪一步实际最慢。
- 当前答案以完整 JSON 返回，前端等待 response.json 后才展示答案/机会图；没有候选阶段的响应。
- 一个进程的 NetworkAgent 使用一个非阻塞互斥锁；另一个问题会收到 busy，而不是独立并发处理。该 demo 预算机制不是生产多用户调度。

依据：adapters/network/agent.py、retrieval.py 与 scripts/onboarding/static/network/assistant.js。本次没有压测或再次付费调用。

### 建议性能设计

1. 离线/后台增量处理：分段、元数据绑定、embedding、倒排索引、可缓存邻接与实体摘要。按数据变更更新，保留快照与纠错/删除传播；不在提问时全量抽取画像或全量重建。
2. 查询分路：姓名、公司、明确条件和普通图展开使用确定性检索；复杂 strategy 才进入模型规划。模型重排只处理有限证据候选，但应分别保留各需求候选，避免为了速度牺牲唯一有效命中。
3. 独立工作并行：同一需求的词法/语义召回，以及不同需求的检索可并行；有依赖的目标规划、检索和合成仍有先后次序。生产使用复用的连接客户端、受限 worker 和按租户限流/配额，不保留进程全局只准一个问题的交互限制。
4. 分阶段返回：先报告实际阶段与已检索的候选/证据图，再显示验证后的策略回答；候选阶段明确标注待分析，不能把未完成核验的文本表现成结论。阶段返回改善等待体验，完整完成时间仍必须单独测量。
5. 缓存与取消：缓存键覆盖租户、权限版本、数据/索引版本、知识日期、查询条件与模型版本；对更新、撤权和删除失效。用户改问或关闭时取消可取消工作，旧请求不能覆盖新结果。共享缓存不可跨权限复用结果。
6. 按预算降级：为规划、检索、重排、核验设置超时与候选/token上限。模型阶段失败时可以保留已授权的原始检索结果并说明未完成分析；不输出伪造策略、不无限排队或自动重复付费调用。不能为省一次 count_tokens 请求而取消输入预算保护；应实测并研究等价安全方案。

### 待验证的体验目标，不是当前性能承诺

目标草案：在约定的数据量与并发下，精确/条件搜索和局部展开 P95 <= 1 秒；复杂问题首批候选/证据目标 2–3 秒；完整策略答案 P95 目标 10–15 秒。后两个目标涉及模型规划路径及 provider 波动，必须测量后决定是否保留两次调用、减少规划输入或调整产品等待预期。冷启动、缓存命中、首次可用结果和完整回答分别统计；动画不计为搜索成功。

### 压测与上线门槛

在授权数据快照或保留真实分布特征的合成集上，建立 Mark 参考规模及 10x/100x 证据量的压力场景；后两者是容量实验档位，不是对老板实际数据量的估计。分别测试单请求及逐级并发（例如 1/5/20，最终值由预期用户数决定），同时包含索引更新、冷/热缓存、长消息、高度数组织和宽泛战略查询。

记录每阶段 trace：排队、计划 token 预检、规划、各路召回、重排、图扩展、证据打包、答案 token 预检、合成、核验、首次结果、总耗时；报告 P50/P95、错误与超时率、队列长度、内存/CPU、provider token/成本、索引新鲜度以及同一配置的召回/归因质量。只测 24 人 demo 或平均响应时间，不足以上线。

下一次实施先加可观测性和可重复基线，再按实际瓶颈优化。生产方案必须同时满足质量、延迟、容量和权限隔离；更多 reranker/模型调用只有在固定预算实验中带来可证明收益才进入默认路径。
