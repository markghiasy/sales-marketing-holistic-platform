# Ironman 研究方案：我们做什么，怎样得到可信结论

2026-09-30 · Eva Ng · 导师讨论版。本文规定拟做的研究，不报告已经完成的实验结果。配套 [英文摘要](abstract-for-supervisor.md)、[技术框架](search-framework.md) 和 [选题理由及导师关联](topic-recommendation.md)。

## 1. 一句话说明研究

研究商业目标包含多项需求时，显式记录“哪些需求已有证据支持、哪些仍未解决”，能否让系统在有限预算下找到更完整、可靠的人脉与资源组合。

研究对象是检索行为和检索结果。Ironman 提供应用背景与实验平台。不会在第一篇同时研究身份消歧、事实抽取、实时图更新、模型训练、图界面和商业成交。

暂定题目：**Evidence-Grounded Multi-Requirement Retrieval in Professional Networks**。

## 2. 从业务需求变成研究问题

示例任务（虚构）：我想推出面向物流企业的 AI 安全产品，需要安全测试经验、物流采购经验和试点接洽渠道。

一个只返回很多安全技术联系人的系统，可能每条结果都相关，却仍漏掉采购与试点条件。另一方面，某人提过采购，不意味着他有采购职责；同公司，也不意味着愿意或能够介绍。

**主研究问题 RQ1：** 在相同信息、证据资格与资源上限下，显式需求状态驱动的检索，相比简单检索与强自适应检索，如何改变有支持的需求覆盖、无依据推荐和成本？

**机制问题 RQ2：** 如果出现改善，是因为搜索过程中重新分配了探索预算，还是仅因为最终结果更为多样，或读取了更多证据？

**边界问题 RQ3：** 需求数量、证据缺失和图中干扰节点如何影响效果？哪些条件下简单方法已经足够？

业务价值对应“少漏重要条件、少做无依据推荐、核查更容易”。本轮检索实验不会证明实际成交率、收入或组织绩效提高。

## 3. 研究方法是什么

主方法是**设计并进行受控比较实验**：实现一个可替换的检索策略，在相同任务与数据上比较不同方法，控制其他变量，分析效果与失败原因。系统设计提供实验对象，正式结论来自评测。

这不是问卷主导研究，也不是仅展示 demo。若导师建议增加真实用户任务，再单独设计用户研究；不能把 Mark 对演示的认可当作用户实验结果。

| 部分 | 本研究如何处理 |
|---|---|
| 自变量 | 检索策略；是否更新需求状态；是否只做最终多样化 |
| 主要结果 | 最终输出有证据支持的需求覆盖，以及无依据推荐情况 |
| 成本结果 | 检索/证据读取量、模型 tokens 与调用、上下文大小、端到端耗时 |
| 固定条件 | 图快照、可用证据、查询需求、时间/审核规则、底层检索工具、输出限制 |
| 分析单位 | 一次查询；同网络/场景下的相关查询按组处理 |
| 压力测试 | 可控的证据移除、需求数量、干扰邻居；所有方法使用同一版本 |

第一阶段直接输入人工确认的结构化需求，避免把 LLM 理解问题的误差混入搜索比较。自然语言解析另行评价。最终解释若使用 LLM，统一模型与提示设置，分别报告检索与生成耗时。

## 4. 要做的方法：最小版本

输入：需求列表、冻结的图快照和预算。

1. 使用共用的关键词/向量检索器取得起点。
2. 为每项需求维护状态：未搜索、候选命中、有支持、冲突或预算内未解决。
3. 根据尚未得到支持的需求，选择继续补召回、展开邻域或读取来源。
4. 只在取得符合主体、范围和时间条件的支持后更新覆盖；词语匹配不自动满足需求。
5. 达到停止条件后输出候选、依据、已有联系路径与未解决条件，记录开销。

第一版的评分和桥接探索规则采用 [框架 v0.1](search-framework.md) 中的有界启发式；权重/阈值只在开发集确定并在正式测试前冻结。当前尚未实现或测得效果，不能把描述当作工作结果。

需求要保留对象绑定。“一个人同时懂安全和采购”不能由两个人分别满足；“找一个互补团队”才允许跨人覆盖。公司需求、个人能力、联系路径分别记录，不做不合法归因。

方法运行时只能看已有记录及公开给所有基线的规则；不能读取测试集 gold support 标签。人工审核事实是否正确，与某事实是否满足具体查询，是两个不同判断。

## 5. 对照组与消融

| 编号 | 方法 | 回答什么问题 |
|---|---|---|
| B0 | Hybrid retrieval + 公共结果组装 | 普通关键词/向量搜索能做到多少 |
| B1 | Hybrid retrieval + 固定有界图展开 | 图结构本身带来多少帮助 |
| B2 | B1 候选池 + xQuAD-style 多样化 | 仅在最后照顾不同需求是否已经足够 |
| B3 | 同工具的自适应 agent controller | 显式状态策略是否优于已有的灵活探索方式 |
| P | 显式需求状态驱动的有界探索 | 待检验方法 |

B3 优先实现与 [ARK](https://arxiv.org/abs/2601.13969) / [ToG-2](https://arxiv.org/html/2407.10805v7) 对应的清楚、可复现适配。记录与原论文的差异，不能把简化实现称为完整复现。根据任务定义加入 [coverage/connection-cost team selection](https://cs-people.bu.edu/evimaria/cs591/lappas09finding.pdf) 的辅助对照；不把最接近的领域方法永久排除。

所有主对照共享来源、时间与审核资格规则。允许基线使用同一查询需求，不能只给本方法有用信息。相同 top-k 或工具调用次数不等于相同计算量：必须额外核算取得和检查的记录、模型消耗及实际延迟。

消融包括 P 不更新需求状态、只作最终重排、去掉桥接探索配额。所有方法保留相同的基本证据资格检查；不能靠关闭其他方法的正确性约束制造优势。

相关工作依据另见 [相近方法笔记](../../research/research_notes/2026-09-30-adaptive-search-related-work.md)。动态探索、需求覆盖和互补组队均已有先例；本实验检验的是具体设计及其适用条件。

## 6. 数据与标准答案怎么来

**诊断阶段：** 先做约 12 个小场景，覆盖单条件、多条件、桥接路径、同名人、旧职位、仅共享公司、条件未知、冲突和多条件主体绑定。这些用于查错，不用于宣称统计优势。

**正式评估：** 先收集独立于方法设计的查询需求，再建立查询—候选—断言—来源的标注。分开训练/开发与测试场景；同模板替换人名不算独立测试。正式样本量在试跑后依据方差、目标精度、标注预算和导师意见确定，并在正式测试前登记，不能看完测试结果后继续加样本直到显著。

优先争取与真实业务任务对应的获授权、去标识案例；工程使用权限不自动涵盖研究和发布。若暂时只能用合成数据，论文明确限定为受控可行性研究，不声称工业成效已验证。公开 expert/team benchmark 是否能提供相符的来源证据需要审查，不能给纯技能标签数据虚构聊天原文。

标注至少包含：需求含义及主体绑定、允许的支持证据组合、证据不足/冲突、路径中的关系语义。记录多个可接受答案，而非只认可我们期望找到的那个人。

评判对方法名称和输出排序尽量盲化。试跑可以由 Eva 主标并让另一位评判者独立复核部分；正式主测试争取双人独立标注并记录分歧及仲裁。若只能单人标注，显式报告限制，不用第二个 LLM 冒充独立人类评审。Mark 是否参与标注需另行商定。

人工移除证据时，同时清理依赖它的断言与索引，固定移除清单，防止摘要或向量文本泄漏被移除内容。金标准区分“原完整场景有事实”和“此实验条件下有可用支持”：隐藏证据后，不能奖励系统凭旧知识猜中。此类实验反映可控缺失，不代表真实资料的缺失机制。

## 7. 具体测什么

| 指标 | 定义与防误用规则 |
|---|---|
| 有支持的需求覆盖 | 输出中满足 gold 支持规则的必需正向需求数 / 必需正向需求总数；另报在当前快照可回答的需求上的召回，避免把资料本来缺失与方法漏检混淆 |
| 全部必需条件满足率 | 在可回答查询中，完整覆盖所有必需条件的比例；按主体绑定判定 |
| 推荐断言精确率 / 无依据率 | 对实际输出的“某实体满足某条件”断言逐条判定；无输出的分母为零，记 N/A，并报告输出量与覆盖，不能算完美 |
| 有效路径比例 | 声称的路径中，关系及来源完整且语义成立的比例；同公司不能算直接认识，没路径可如实说明 |
| 缺口表达错误 | 将未知当成已满足、将预算内未找到当作全网不存在，分别计数 |
| 成本与速度 | 实际记录/边读取、模型 tokens/调用、输出大小、检索及端到端 P50/P95；冷/热缓存与索引构建成本分开 |

正向 coverage 不包含 exclude 条件；排除规则及其他硬约束另报违反率，未知也不自动算通过。方法自身估计的 coverage 不能代替独立判定的最终 coverage。

固定不同预算档位，报告质量—成本曲线；主要策略对比以 P 与强自适应 B3 为重点，同时展示简单方法。对同一查询配对比较；按网络/场景聚类估计不确定性，避免把大量相关改写当作独立样本。若只有一个网络，明确外推限制，不声称跨组织普遍有效。

正式测试前登记主指标、主对比、预算、参数、重复运行规则和分析方法。报告效果量及置信区间；小样本不确定时直接说证据不足。随机模型需固定可控设置并重复运行，保留完整运行轨迹。

## 8. 研究结论现在是什么

**目前没有新方法有效性的研究结论。** 已有的是产品动机、demo、相关工作和本研究设计。存储计时、Graphiti 接受测试、早期七个构造案例不是这项检索研究的结果。

下表是未来可能的结果及允许的结论，不是预期结果承诺：

| 观察到的结果 | 可以说什么 | 不能说什么 |
|---|---|---|
| 相同预算下覆盖提高，且无依据率没有明显恶化 | 在测试条件下，该策略改善有支持的覆盖与可靠性取舍 | 商业收入提升；所有图任务都更好 |
| 只在多需求/桥接任务上改善 | 方法有特定适用范围，可以据此选择搜索策略 | 全面优于普通搜索 |
| 覆盖提高但模型消耗和等待也明显提高 | 找到了质量—成本权衡，需要说明收益是否值得 | 更高效、更快 |
| 只比固定展开好，与强 agent 无可分辨差异 | 当前证据支持优于该静态基线，对强对照未建立优势 | 证明了新的自适应算法优越性 |
| 没有明显收益或更差 | 在当前条件下不支持该方法优势；分析冗余、误判、路径与预算原因 | 所有显式需求方法都无效；或把不显著说成完全等价 |
| 检索改善，但真实用户任务没有改善 | 离线指标的改善尚未转化为已测用户效益 | 工业效益已验证 |

可以形成的最终结论形式：**在什么数据和查询条件下，采用什么机制，以什么成本，改善了什么指标；在哪些条件下没有改善。** 结论不需要保证方法胜出，但必须让读者获得此前不清楚、又有证据支撑的认识。
