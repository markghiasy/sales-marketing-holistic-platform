# Eva 本地生产：真实数据 Network 接入设计草案

日期：2026-09-29。状态：Eva 已同意真实源只读适配、本地持久化与并排验收的接入方向，并补充 Inbox 持续更新要求；本文已补充运行频率与增量一致性设计，尚未部署或修改生产数据库。用户已明确：生产应用继续在本机运行，使用自己的真实数据，不安排云端迁移。

> 2026-09-29 后续实测：[存储与 Graphiti 评估](../../research/reports/2026-09-29-graphiti-storage-evaluation.md)支持优先关系型知识存储，暂缓 Graphiti/Neo4j 核心替换。本草案的只读来源、独立派生层、证据/审核与版本边界保留；原 SQLite 派生库选择尚需与实测 Postgres 候选统一，不能把评估结果当成已经实施或数据库已迁移。

## 目标与验收对象

让 Eva 在现有本地 Comms 工作流中使用真实 network：联系人/组织图、四范围展开、源证据、搜索、逐步形成的战略画像与策略问答。保留既有身份解析、消息导入、Inbox 隐藏/合并行为。生产能力不能只是给 ScenarioStore 换一个 JSON；必须支持持久化、可更新来源、清晰的数据身份和失败恢复。

既有生产 app 的真实服务目前在 127.0.0.1:5001。5000 是别的响应，不能接管。5055/5056 是 synthetic demo，继续隔离。准备阶段另选空闲 loopback 端口验证，验收通过后才把 network 路由和入口并入现有生产 app。

## 方案比较

1. 直接替换 demo 的 fixtures：最短但不满足持久化、真实身份和证据语义，不采用。
2. **真实源库只读适配 + 本地可重建索引/派生记录 + 复用 network UI（推荐）**：先保护现有采集与解析流程，独立验证后集成本地 Inbox；适合当前单人使用。
3. 立刻更换整个存储和部署平台：影响面大，对当前数据量尚无实测必要性，不采用。

## 推荐架构

现有消息/身份/fact/LinkedIn 数据 → 只读 SourceRepository → canonical entity / source evidence 适配 → 持久化 NetworkStore 与检索索引 → NetworkService → 同一套图、证据、搜索、策略界面。

- SourceRepository 使用显式只读连接、超时和复用连接/受限连接池；查询字段与表明确列出，不读取 message.raw。
- 首次导入记录一致快照和来源游标；派生库位于独立 gitignored 本地数据目录。以 SQLite 持久化 source IDs、索引状态、画像草稿及审核事件，针对当前单机单写工作负载；先验证 SQLite/FTS 支持及读写恢复。该选择不等于云端/多人最终存储选型。
- 索引属于派生数据，可从来源重建；人工审核事件不属于可随意丢弃的缓存，必须备份、版本化并支持恢复。存储接口隔离，以便日后改用专用 Postgres 存储，而不重写 UI。
- 重建索引在后台完成；查询读上一个一致版本，成功后原子切换。源库断连时显示最后成功版本和时间，不清空数据或退回 fictional fixtures。
- source/channel ID + canonical identity 映射保持稳定。合并/撤销合并会使受影响的事实、索引、缓存和审核主体映射失效并重新投影，不能只跟踪新消息时间。
- 适配 synthetic 与 real Store 协议，复用投影/呈现逻辑；真实模式禁止加载测试 fixtures、simulate/reset API 及硬编码人物、项目、日期。提供明确 data_source 标签。

## 真实图与四个范围

1. **直接往来**：以 self identity、发送者、接收者和消息方向推导。仅被同一群发/CC提及不是相互直接往来；群聊/多收件人不自动两两连边。保留原始参与者与覆盖范围；同一消息不因 join 多行而重复计数。
2. **合作/介绍**：只使用有可定位证据且已审核的关系。当前结构化源库没有这类已审记录，初期为空或标注尚未提取；不从 ai_brief.graph 的自然语言名字直接生成 confirmed 边。
3. **项目/团队**：项目实体、成员与职责需要来源及消歧；目前没有完整可直接迁入的项目表。先按原文抽取候选和人工审核，不凭同一话题自动认定共享项目。
4. **组织/公司**：复用 organization IDs 和 confirmed works_at，保留 LinkedIn 快照来源。has_title 是角色字段，不是预算权限。自报岗位不是独立核验的事实；时间未给定时显示未知，不能编造有效开始日。

Known by 使用来源 ingested_at/extracted_at/reviewed_at，事件时间使用 sent_at 等原始字段。没有保存历史版本的结构化源快照，不伪装成精确历史可回溯。范围可重叠，互动仅对精确人物对计算；不足的关系显示未知。

## 数据和模型边界

当前生产已有 ai_brief/Anthropic 接入，network 问答沿用已配置的商业 API。界面明确说明策略问答会发送经检索选出的原文片段及相关身份/上下文到 Anthropic；本地部署不宣称离线模型。默认只在明确提交战略问题时调用，不在输入时偷偷调用，不默认全库重新生成摘要/画像。

首次真实问答只发少量所需片段并受既定 token/调用预算限制。模型生成的关系/画像一律 pending，审核状态持久化；引用存在/原文匹配/已审核都不自动证明语义正确。画像提取采用可暂停的小批次，先提供预估规模和上限，不自动花费全库抽取成本。embedding 供应商尚未选择，不能默认把现有 Claude key 当 embedding 凭证；第一阶段没有新的外部供应商。

策略原文必须以实际主体绑定；组织的需求与联系人自身能力分开。其他联系人被提到，不等于已确认身份或有合作关系。用户纠错、拒绝和撤销必须在后续检索中生效。

## 搜索与速度

- 初期已有原文和结构化元数据即可建立持久化词法索引，避免每次请求遍历构建全部记录。确切身份、名称和已有条件走确定性路径；strategic 问题才调用规划器。
- 用 SQLite FTS 的可用能力建立首个生产基线，明确分词和中文支持边界；不能把 FTS 默认配置当成已完成多语言混合检索。完整 BM25/dense/RRF/reranker 研究按后续实验逐步引入，不作为真实数据首次读通的前置大改造。
- 限制 planning catalog：先通过名称/上下文/索引找到候选，不发送全部 1,532 个联系人。每需求保留独立候选以避免稀有需求被截掉。
- 源数据同步、画像抽取、索引维护都不在用户请求的关键路径做全量工作。增加检索/模型/token预检/图扩展/总耗时记录；日志不记录原文、密钥或含凭证 DSN。
- 独立检索可并行；服务端采用有界并发与超时，不保留整个应用只准一个问题的全局 demo 锁。超时明确返回已找到的证据及未完成阶段。
- 分阶段展示真实候选/证据，不把尚未核验的回答流当成最终事实；缓存键包含用户/来源库指纹、权限与数据版本、日期、条件及模型版本。
- 先按 Eva 的实测量验证，再做 Mark 参考量和 10x/100x 合成证据扩容试验。性能目标参照研究报告第7节，尚不承诺达标。

## 持续更新：实际频率与一致性

### 2026-09-29 本机只读核实

查询 Windows Task Scheduler 的 CommsPlatform 任务及本地状态文件，没有启动同步或修改任务。以下是配置频率，不是承诺的端到端延迟，也不代表 Mark 机器的实际配置。

| 来源 | 实际计划 | 核实结果 |
|---|---|---|
| Outlook | 每 10 分钟 | 01:50 任务结果 0；采集状态 ok |
| WhatsApp | Node 收消息到文件队列；Python 每 10 分钟入库 | 01:56 入库任务结果 0；连接状态 connected，01:57 心跳仍刷新 |
| LinkedIn 消息 | 每日 09:00、12:30、15:30、19:00 | wrapper 默认增加 0–15 分钟 jitter，可由配置调整；28日后两次任务结果 1 |
| LinkedIn 连接人导出 | 独立导入流程 | 不能把消息采集频率当成 Connections 导出更新频率 |

LinkedIn 19:10 的 .sync_status.json 是 ok，而该任务最终返回 1。代码在身份解析、人物键查询、摘要处理之前就记录采集 ok，因此这两个信号不是同一阶段；当前尚未诊断失败原因，不能断言消息采集失败或整个流程健康。现有监控仍应保留，network 状态应把来源同步、派生同步和画像抽取分别显示。

代码依据：repo/adapters/store_writer.py 的新消息 insert 后执行 pg_notify('inbox_updated', message_id)；repo/scripts/onboarding/app.py 的 /inbox/events 监听该频道，并由现有 Inbox SSE 刷新列表。消息提交与后续 resolution/brief 并非同一事务。新消息通知不能代表身份解析、画像或整张图已就绪，也未覆盖现有消息的修改、删除和身份改名/合并。

### 初期方案：通知唤醒 + 持久化任务 + 定期对账

继续遵守源库只读接入。复用现有通知唤醒单个后台 worker，在本地 SQLite 持久化待处理对象与处理版本；不在 Flask 请求里做同步，不为每个浏览器开一个同步 worker，也不新增每分钟外部平台抓取。当前规模不引入 Kafka 或完整 CDC 基础设施。

通知只是加速信号，不能充当可重放的消息队列。Postgres 只通知当前监听连接，事务提交后才交付；worker 启动应先提交 LISTEN，再读取快照，允许重复处理。连接断开后必须重新核对源库。依据：[NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)、[LISTEN](https://www.postgresql.org/docs/current/sql-listen.html)。

初期可配置默认值，作为实施和测试基线，不是已达到的 SLA：

- 通知合并窗口 2 秒，持续流量下最多等 10 秒即处理一批；每批最多 500 条来源消息，积压继续分批。
- 每 60 秒检查新入库消息，采用 ingested_at 与 id 的复合游标并回看 24 小时，按源 ID 和内容版本去重。不能按 sent_at 取增量：今天导入两年前的消息也必须入图。
- 每 5 分钟比较 identity/person/fact/organization/linkedin_connection/contact_hidden 的所需字段指纹，捕获无新消息的改名、合并、撤销、审核、组织变更和隐藏；只重新投影受影响对象。
- 启动、重连及每 15 分钟做完整来源清单对账，分批比较 message/participant 的相关字段指纹和 ID 集合，捕获更新、硬删除、极晚提交及超过回看窗口的变化。正文留在源库/本地存储，不进入诊断日志；对账会扫描来源，必须测成本。该方案以当前 7,338 条为起点，扩容时不能盲目沿用全表扫描频率。
- 对账在一致的只读快照内完成。只有全部分页成功，才能认定某条已删除；分页失败、权限变化或源库切换都不能把缺失页当成删除。源库指纹变化应停止并重新绑定，而不是清空已有数据。
- 本地批次事务同时提交源记录、来源到实体的依赖、图和词法索引变更、任务状态及 checkpoint；成功后才增加 data_version 并通知前端。崩溃后安全重放，旧任务不能覆盖较新的内容。

复合时间游标和回看窗口都不是绝对无遗漏保证：ingested_at 的生成时间可能早于实际提交时间；较早开始、很晚提交的事务可能落在已推进游标之前。周期完整对账承担最终补偿，不能省略。没有源库持久变更日志的第一阶段，修正/硬删除最长可能到下一次成功对账才可见；UI 必须如实显示 last_reconciled_at。若这个延迟不满足使用要求，需要升级下面的 outbox，而不是宣称实时一致。

### 什么发生变化，更新什么

| 变化 | 自动处理 | 不应自动做的事情 |
|---|---|---|
| 新消息、历史补录 | 原文索引、正确参与者、联系人的互动指标与相关子图 | 不把消息直接提炼为已确认能力或合作 |
| 名称/身份归并/撤销 | 稳定来源 identity 重映射；刷新两边节点、相关边、检索与缓存 | 不按显示名合并；不把合并前的画像永久贴给新主体 |
| 事实/组织快照改变 | 新旧版本及来源保留，重算相关共享背景 | 不把两家先后任职公司都无条件展示为当前任职 |
| 原文修改或删除 | 失效对应索引和依赖引用；已提取断言变为待复核或撤回 | 不因过去人工确认过就继续用已失去支持的证据 |
| 用户拒绝/纠错/隐藏 | 持久化审核与可见性规则；影响搜索、图和模型上下文 | 不因下一次重建覆盖审核结果；不让隐藏联系人经策略问答重新出现 |
| 时间自然流逝 | 按查询时间计算时间窗与互动衰减，缓存包含时间粒度 | 不等下一封消息才让过期互动降权 |

LinkedIn structured_facts 当前只追加未见过的 works_at/has_title，旧职位没有自动失效机制。真实投影应把当前连接人快照与累积事实分开，旧事实标记来源/时间未知或存在冲突；从导入时间不能推算实际离职时间。

### 确定性更新与 LLM 更新分开

确定性路径不调用模型，目标是正常低积压时新消息提交后 30 秒内图/搜索可见；若通知不可用，则通常由 60 秒补偿检查接手。需要实测后才承诺。此目标不含来源平台到 Inbox 的采集等待，也不包括画像提取。

画像提取任务按 source_id + content_hash + extractor/prompt/model_version 去重，显式开启且有额度；首次接入不自动全库抽取。新断言 pending，旧断言受源内容或主体变化影响时必须重新核验。审核日志独立持久化：同一来源版本的 rejected 不因重复导入复活；新来源版本允许生成新的候选，但不能继承旧 confirmed。常规 Inbox 更新和证据搜索不等 LLM 队列。

长耗时问答绑定一个 data_version，并记录真正使用的证据及主体映射指纹。模型返回前重新检查这些依赖：相关证据已删除、更正、隐藏或重映射，拒绝发布旧结论并提示重新运行；其他无关联系人新消息不必让回答作废。发送原文前也校验本次选中证据仍可用；源不可达时可以看明确标记的旧图，但不新发未经当前校验的真实原文。历史回答保留生成时版本，发现其引用失效后标记，不静默改写对话。

UI 分开显示来源最近成功同步、graph last_applied_at、last_reconciled_at、pending extraction 数与失败重试状态。当前图在新版本提交后只补丁更新改变的节点/边，保留布局、选中人、缩放和筛选；显示“新增 N 条关系/来源”，避免重排整张图打断操作。历史 as_of 视图保持固定。

### 上规模后的升级边界

如果对账开销或修正延迟超出实测预算，下一阶段再为源库增设 transactional outbox：来源写入与变更行同事务提交，涵盖消息/参与者/identity/person/fact/隐藏和 merge/reverse；worker 维护独立消费状态。不能简单用自增 ID 最大值当提交顺序并跳过较小但晚提交的事件，须采用可重放未处理事件与幂等确认协议。此升级涉及源库迁移及所有写入点，另行做兼容与回退评审，不混进第一阶段只读适配。

### 验收补充与接入前风险

必须测试重复通知、离线通知丢失、重启半批次、同时间戳分页、很晚提交、历史补录、同名联系人、多参与者、合并再撤销、无消息的名称/事实变更、部分对账失败、源证据删除、模型回答期间来源变更、以及持续更新下的搜索延迟。模拟时钟控制 60s/5min/15min 调度，不用真实等待。

另发现 Outlook sync.py 在 conn.commit() 之前写出 folder delta link；如果后续事务失败，游标可能先于消息持久化。这是静态审查发现的失败窗口，尚未证明实际丢消息。生产接入前应修正为数据库提交成功后再保存游标，并测试失败重放；不需要改动用户的现有 token、触发即时外部同步或重跑历史导入。

## Inbox 标签、summary 和 context 的刷新闭环

### 当前代码实际如何工作

- 三个渠道 sync 收集 touched_identity_ids，消息提交后执行 resolution，再映射 person_keys，依次调用 ai_brief.refresh_touched_best_effort。
- 每个 touched 联系人一次生成：读取其跨渠道可用消息历史、非 rejected 的结构化 facts 和互动统计，调用 Claude 同时产出 summary/context/topic/graph/urgency，成功后覆盖该联系人的 ai_brief 缓存。默认模型 Haiku 4.5，ANTHROPIC_MODEL 可以覆盖；读取页面不调用模型。超出 160,000 输入 token 时当前代码逐步丢弃较早消息，直到符合预算或明确跳过。
- summary 是当前需求的一句话；context 是相关背景列表；topic 是 1–3 词的当前话题，也是现有真实 Inbox 的单个标签。它们不是三个独立刷新任务。
- synthetic network 多标签由 contact_tags 从 confirmed claims/profile_assertions 及有效证据投影，包含关系、职能、行业、组织、项目；不根据新消息自动生成。demo summary 使用节点 role，topic 和 context 含演示文本，不能当成真实自动摘要已完成。
- 当前新代码生成失败时保留上次成功 brief，尝试在 ai_brief_status 记录 failed/skipped/truncated 并提示。源库 schema 不匹配时状态写入本身会失败，不能把它误报为模型不可用。

代码来源：adapters/ai_brief.py、adapters/store_writer.py、三个渠道 sync.py、adapters/inbox_query.py、scripts/onboarding/templates/inbox.html、adapters/network/search.py、scripts/network_demo.py。

### 查到的覆盖缺口

1. upsert 返回发送者 identity；sync 把这个返回值加入 touched，随后过滤 self。只有用户主动发出消息时，对方收件人可能完全不在刷新名单。测试要覆盖“我回复了，对方还未再次发消息”，不能只测 inbound。
2. 同一条已存在消息重放也会返回发送者并触发 touched；没有输入指纹跳过逻辑，可能重复花费。gather_input 的参与者 join 未做消息 ID 去重，同一人的多个 identity 同时参与也可能重复输入。
3. 新消息提交就发送 inbox_updated；brief 随后才生成，完成后没有独立通知。前端 SSE 仅刷新列表，已打开的详情 context 不随之更新。这导致消息新、摘要旧，即使后台最后成功。
4. 合并迁移的是两边较新的缓存，不等于基于合并后完整历史重算。只改 facts/名字或撤销合并也缺少统一摘要失效队列。
5. 逐联系人串行调用，缺少持久待处理队列、输入版本核验和新旧任务防覆盖；“成功生成过”不等于“覆盖最新消息”。context 是模型生成的文本列表，目前没有逐句来源 ID，不应直接晋升图谱 confirmed 事实。

### 接入后约定

把联系人多标签、短期摘要和长期背景定义为三个产品对象，共用证据和版本体系：

| 对象 | 来源与更新 |
|---|---|
| 当前话题与 summary | 相关消息变化后按联系人合并任务；异步重算，旧结果显示等待刷新/失败及覆盖版本 |
| context | 同一 brief 任务生成，但基于原文、有效结构化事实和未完成事项；每项支持可检查来源。新消息可关闭旧承诺，不能只在旧摘要上追加摘要 |
| 多标签 | 结构化组织/关系/项目和画像断言的投影；非结构化候选先审核；显示话题不等于认定技能 |

默认继续以一份有预算的联系人输入一次产出 brief 各字段，不为 summary、context、topic 各发一次模型请求。由 source/content fingerprint、主体映射、prompt/model version 确定是否需要重算；只收集真正受影响的非 self 联系人，包含 outbound recipients，群发规则与图谱一致。

本地派生 store 持久保存 brief job、最后成功内容及其来源版本、attempt/error、生成时间与证据依赖。成功提交后发布 brief_updated，列表和当前打开的详情按 person_key 更新且不丢阅读位置；失败保留明确标旧的上次内容。基于旧输入的慢任务不得覆盖新结果。来源修改/删除后，旧 context 与标签引用都必须失效。

候选验证期间复用现有 source ai_brief 作带来源时间的兼容展示，不再自动调用一套新的全库摘要。正式切换时引入 AI_BRIEF_REFRESH_MODE=inline|queued，默认 inline 保持既有行为；明确切到 queued 后才由统一后台 worker 接管摘要，三个渠道 inline 刷新停用。重启后的未完成任务可恢复；不得让旧同步脚本和新 worker 同时对同一联系人重复生成。源库保持只读的 network 约束，新 brief 存本地派生库并由 Inbox service 覆盖读取；回退到 inline 的配置和缓存显示规则必须验证。

### Knowledge graph 变化策略 v1（拟定规则，待产品确认）

研究补充（2026-09-29）：已完成 [知识图谱更新策略一手资料调研](../../research/reports/2026-09-29-knowledge-graph-update-policy.md) 与固定版本源码核对。后续建议把认识性质、审核状态、现实有效期和系统记录时间分开；评估低影响自述能否以未核实来源陈述自动可查，避免长期全部人工审核。该扩展尚未批准，不改变下面的初期保守发布规则。资料区分 Graphiti/Mem0 论文、历史实现与当前代码，没有运行性能或真实性评测。

Eva 澄清：核心缺口是知识图谱本身的变化策略，不能先从标签刷新反推。此前的 worker/对账方案只解决何时发现变化；本节定义允许改变什么、按什么依据发布。它是追加的拟定政策，不应标成已确认或已实现。

#### 四类独立记录

1. **来源版本**：保留稳定 source ID、内容版本和删除状态；记录 sent_at（事件时间）、observed_at（本系统获知时间），来源正文按既有留存/删除政策处理。历史审计不意味着无限保留被删除原文。
2. **断言**：主体—关系/属性—对象，加项目/组织等适用背景、时间区间、证据引用和身份解析状态。断言是可被支持或反驳的命题，不等于事实已成立。
3. **变更提案与审核事件**：把新增、增补证据、缩小适用范围、终止、取代、冲突、撤回记录为显式操作；记录理由和前置版本，可重放，不能只保存最终 JSON。
4. **当前/历史投影**：按查询时间、有效性、来源可见性与审核政策生成图、标签、搜索和 agent 上下文。互动频率、衰减、推荐排名属于派生指标，不直接改写事实。

#### 从新消息到发布

来源记录提交 → 稳定主体绑定和来源去重 → 自动更新可直接观察的互动 → 对有语义变化可能的来源生成有预算的候选 → 校验主体、原文、否定/引用/计划语气、时间和上下文 → 与现有断言比对 → 执行规则允许的变更或进入审核 → 原子发布受影响投影。

第一阶段语义抽取仍按已约定的显式开启和预算执行，未开启时新消息只更新原文检索和确定性关系，并标注语义处理尚未覆盖。不能把关键字筛选或模型“不发现变化”当作没有知识变化的证明。

#### 变更操作与默认权限

| 操作 | 条件及处理 | v1 自动化边界 |
|---|---|---|
| 无语义变更 | 问候、重复导入、与主体无关的提及等，不产生人物画像事实；正常新互动仍记入活动 | 来源去重自动；语义无变更只是本次提取结论，可补查 |
| 新增断言 | 已解析主体的新关系/属性，或新时间/项目背景下的命题 | 明确直接互动可自动；原文语义抽取一律 pending；未知主体保留 unresolved，不按同名绑人 |
| 增补支持 | 同一规范化命题、同一适用背景、兼容时间的新证据 | 完全相同来源版本不重复计入；结构化等价支持自动归并，LLM 判断的语义等价支持需校验/审核后归并 |
| 修改/细化 | 原“参与项目”细化为“负责项目某部分”，或补充明确有效期 | 生成带前置版本的变更提案，保留旧命题及变更关系，审核后发布 |
| 终止/取代 | 离职、退出项目、任务完成、明确由新状态代替旧状态 | 语义提案审核后关闭/替代当前适用区间，保留历史；不能仅因出现新公司推断离开旧公司，可能兼任 |
| 冲突 | 在相同主体、时间和适用背景中无法同时成立的证据 | 不采用“最新消息必胜”或“LLM 分数更高必胜”。保留双方支持及争议；未经证实的疑似冲突不直接撤销已确认事实，策略推荐提示不确定、关键决策需核实 |
| 撤回/纠正 | 来源删除/更正、用户拒绝、错误身份合并撤销 | 来源完整对账确认后自动撤回该来源的支持，保留其他有效支持；用户纠错立即影响投影。失去全部有效支持的事实不再作为当前可用事实 |

确认语义操作时必须检查其前置来源/主体/断言版本；过时提案不能覆盖新状态。一次用户操作可以审核同一来源的一组相关提案，但发布事务不能产生一半结束旧任职、一半新增任职的中间状态。

#### 避免把聊天误变为能力画像

- “我在找安全测试负责人”是需求候选，不是发言人的安全测试能力。
- “Sam 做过这类项目”是关于 Sam 的第三方陈述，先解析 Sam 身份并保留说话人；不把能力写到发言人身上。
- “如果启动项目，我可以帮忙”是条件性意向，不是已发生合作或既定项目成员关系。
- “我们以前做过 Project A”允许形成历史经历候选，不自动变成当前成员。
- 同一公司/项目/群组仅更新相应背景，不升级为直接往来、熟悉或可介绍关系。
- 本人自述、第三方评价、结构化来源和用户确认分别保存；审核通过不是对能力或商业权力的独立验证。

#### 时效和可信程度

互动强度可以按时间衰减；已发生的经历不因近期没聊天而被删掉。预算、需求、当前职责、可用性等时效性信息可标记“需重新核实”，但“久未提及”不是“已结束”的证据。v1 不设一个适用于所有字段的统一过期天数。

支持证据增加与交往更频繁是两个不同指标；同一消息被跨平台转发、被引用或重复导入不能作为独立支持累加。第一阶段可确定的同源引用去重；无法确定独立性的来源标注未知，不声称概率置信度。所谓 confidence 不能单凭模型自评分作为自动发布依据。

#### 例子：项目职责的演进

初始已确认“Alex 参与 Project A”。新消息“我现在负责 A 的交付”生成职责候选；确认后发布角色边和标签。随后“交付已由 Sam 接手”生成 Alex 角色终止及 Sam 角色新增两个相互关联的提案，Sam 身份不明则保持 unresolved。审核前不直接把 Sam 当负责人进行推荐；审核后同版本结束旧职责并建立新职责。Alex 曾经负责的历史保留。若原消息被撤回，则重新核对各项支持，不简单删除所有相关人物或整个项目。

### 多标签随图更新：同一事实来源，稳定展示

Eva 已明确要求真实 Inbox 使用新版 demo 多标签，并指出新消息更新图谱也会改变标签。标签作为图谱事实/画像的展示投影，不维护第二份由 LLM 独立生成的自由文本标签列表。summary/topic 的生成结果不反向写 confirmed 标签或边。

同一 data_version、as_of、可见性和审核规则决定 graph、contact tags 和搜索条件的资格。新消息的直接互动边可以先更新，但未审核的语义候选只出现在待审核视图，不会自动变成正式职能/技能/合作标签。这不是要求所有图谱变化都改变标签：只有影响标签支持事实的变化，才重算对应联系人的标签集合。

| 新消息例子（虚构） | 应发生的变化 |
|---|---|
| “最近在看 cybersecurity 产品” | 更新话题/summary；不生成“安全专家”能力标签 |
| “我负责 Project A 的技术交付” | 生成带原文的项目/职责候选；审核后图中关系与对应标签一起可用，来源仍标为本人自述 |
| “Project A 已经交接，我不再负责” | 生成对既有职责的变更/冲突候选；不能未经审核抹掉旧事实，也不能把已检测到争议的职责继续当无争议当前能力推荐。当前标签提示存在待核实变更，在历史中保留以前的职责；确认后关闭旧有效区间，日期未知则明确未知 |
| “谢谢，收到了”或重复导入同一消息 | 正常更新相关活动记录；没有标签依据变化就不改标签，不重复抽取相同版本 |

标签身份使用 canonical person + facet + relation + canonical value/entity 的稳定 key；显示名改变不制造新标签。多条来源支持同一标签时合并展示并保留支持集合；撤回一条来源后如果仍有有效支持，不删除整项标签。证据删除、审核撤回和明确过期必须及时改变资格，不以“保持 UI 稳定”为理由保留无效结论。

每个标签暴露 source IDs、支持断言 IDs、审核/争议状态、有效期及获知时间。confirmed 表示按当前审核政策接受，不等于独立验证；自述职位或经历应能看出来源性质。新消息中的语义冲突仍可能漏检，因此不能声称系统自动保证所有标签真实和最新。

列表显示策略沿用 demo 的最多 3 个标签加 +N，topic 保持为单独的“当前话题”文字。默认类别顺序固定为关系、职能、行业、组织、项目，同类别按稳定 key 排序；只有已展示项失效或用户改变偏好才替换仍有效的已展示项，新标签先进入 +N 并提供“标签已更新”提示，避免一次新消息使联系人看起来完全变了。详情展示完整标签和来源，支持把有效标签置顶/取消置顶；置顶是展示偏好，不修改事实或阻止过期/撤回。

图、标签和搜索索引在同一本地发布事务更新，前端按版本接收更新，过时事件不能覆盖较新结果。brief 异步完成可以晚于图谱；UI 分开显示其覆盖时间，不伪装成所有内容同一时刻刷新。用户不需要对每条消息审阅，只对新增或变化的语义断言处理去重后的候选。

## 接入与回退

- 在隔离 worktree 开发，保留 repo 的用户改动和现有运行进程。
- 先启动仅绑定 127.0.0.1 的候选版本，数据目录和端口与 synthetic 分离；限制 Host、Origin、请求大小和跨站写入，生产真实记录不出现匿名公开入口。
- Inbox 入口通过明确 NETWORK_ENABLED 配置集成，synthetic 标记与功能开关分离；保留隐藏、合并、阅读等原行为。合并仍使用原 resolution 流程，network 不另写合并算法。
- 对缺失的现有数据库迁移，先制定逐个兼容与备份/回退方案，再决定必要操作；不批量重跑全部迁移。优先让首次 network 接入只读源库，以缩小影响。
- 候选版本通过验证后，再审阅具体切换命令、环境差异和回退入口。不能直接重启正在使用的生产服务来试错。

## 验收标准

1. 数据库聚合计数与接入报告口径对齐；确认实际运行配置对应正确源库，而非 2 条消息测试库。
2. 确认 real UI 无 synthetic 人物/项目、默认固定历史日期、simulate/reset 或内存-only 审核。
3. 同名不同人不误并，多 identity 合并与撤销可追踪，self identity 不被当联系人；群发/CC不生成虚构直接联系。
4. 随机抽查真实联系人、组织及原文来源；不足的项目/合作证据为空或未知，不能补造。
5. 结构化来源可追溯到原导入条目；消息事件时间与获知时间分开；晚到数据和修正无未来泄漏。
6. 查询、索引更新和断线恢复测试；审核状态在重启后保留；删除/更正后旧索引与缓存不继续暴露内容。
7. 普通测试使用隔离测试库和虚构数据；真实数据 smoke 只读。真实正文、索引、截图和密钥不进 git 或研究产物。
8. 真实模型测试有限次数与输入预算，输出核对实际主体和引用支持，不能把来源相关性当能力验证。
9. 当前规模延迟实测与分阶段 trace；并发和扩大规模分别报告。未满足门槛时不称为完成生产发布。

## 本轮边界

已完成：只读数据规模、schema、端口、服务/API计数与测试库区分。未完成：真实 NetworkStore、索引、真实画像接入、生产切换与性能验证。此设计可审阅，下一步据此编写可执行实施计划，不把调研完成当成接入完成。
